How to read this

This report is updated by hand, usually after a release, so the development version in it can be older than the current main branch. The suite is performance/benchmarks.jl in the ProbNumDiffEq.jl repository.

Each benchmark is one full fixed-step solve of a test problem, with the same steps in every version, so a change is a change in cost per step. “Filter only” is the solve with smooth=false; “filter + smoother” is the same solve with smooth=true, so it includes the filter pass.

−40% means 40% less time (or allocations, or memory), ×3 three times as much, ÷3 a third. In “Check a change” every number compares the revision with the baseline. In “History” every cell compares a version with the baseline you choose there, the latest release by default.

Time is the fastest of all solves of a benchmark. Slower solves are those hit by garbage collection or by other load on the machine, so the fastest one is the most repeatable: between releases with nearly identical code (v0.16.5, v0.16.6 and v0.17.1) it differed by at most 8%, while the median jumped by up to 13%. A time difference under 10% therefore counts as within noise. Two runs of the same commit on different days differed by up to 11%, mostly in the same direction, so a comparison is most reliable when both revisions were measured in one session, as just perf does. A larger one is marked ? and hatched when the lower quartile of the solves does not show it too, so it may be a fluke. Allocations are a count and memory is the bytes allocated per solve; both are deterministic, so any difference above 1% counts.

Releases that no longer install on the current Julia run on an older one. In “History”, their numbers are as measured on that older Julia, so against a baseline on the current Julia they include the effect of Julia itself. The release that runs on both appears twice, side by side, which shows that effect alone. The headline there multiplies the overall changes of the package's own steps, and reports the Julia step separately. An overall change is a geometric mean over the benchmarks two versions share.

The changes by kind of benchmark group the benchmarks by the covariance structure of the solver (Kronecker: EK0; block-diagonal: DiagonalEK1, MatfreeEK1, EK0 with a multivariate diffusion; dense: EK1, ExpEK, RosenbrockExpEK), by problem size (d ≤ 3 or d ≥ 14), and by smoothing. A line appears when at least two thirds of a group changed in the same direction.

— means the benchmark could not run in that version, usually because the solver or feature did not exist yet. performance/README.md lists the reasons.
